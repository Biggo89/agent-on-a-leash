Agent on a Leash · Wallet Control Layer

LEASH on the card rails

The issuer decides before the payment, while the cart is still visible, and then holds the card authorization to that decision. The only model in the system writes the policy. It never sees a payment.

Architecture

Where LEASH sits between the cardholder, the shopping agent, the merchant and the Visa or Mastercard network. Numbers follow one purchase from start to finish.

Once, when the cardholder sets the rule

  1. 1The cardholder writes the rule in their own words in the issuer's app.
  2. 2The compiler drafts a policy IR, quoting the words each rule came from. The cardholder confirms it, and it becomes the mandate.

Every purchase, before money moves

  1. 3The agent sends cart, merchant and amount to the connector, with an OAuth token the cardholder can revoke.
  2. 4The engine runs every check against the mandate. Pure functions, no model.
  3. 5If something can't be settled from the evidence, the cardholder gets a push and answers with a passkey.
  4. 6On approve, the network mints a token limited to this merchant, this amount and a short expiry. The agent gets it with the verdict.

At authorization

  1. 7The agent pays the merchant with the scoped token.
  2. 8Merchant, acquirer and network run a standard ISO 8583 authorization.
  3. 9The issuer's host hands the request to the binding.
  4. 10Token, merchant and amount match the approval record: approve. Anything else: decline. Both are logged.

Why two checkpoints

Most of what the engine checks never reaches the card network. This is what each hop can see.

So the item-level checks run at step 4, and step_up can only happen there. At step 10 the issuer has no cart to look at. It checks that the payment is the one it already approved.

Inside the decision engine

A real instruction from the challenge pack, followed through both halves. Only the confirmed mandate crosses the line.

When something fails

What failsWhat happens
LLM provider down, or key expiredThe compiler falls back to the regex baseline. Policies get less detailed; enforcement is unchanged.
Issuer host unreachable at step 9The network's stand-in processing decides alone. The limits minted into the agentic token at step 6 (merchant, amount, expiry) still hold.
Agent compromisedThe cardholder revokes it in the app. Its OAuth grant and mandates are revoked and the next request gets 401.
Merchant charges more, or from another merchant IDThe binding finds no matching approval and declines.
Merchant shows one cart and ships anotherNot caught by the binding alone. Closing it needs the approved cart signed and bound into the token request, as AP2 cart mandates propose. Open gap.

Rollout

Each phase works on its own. Nothing in phase 1 waits for the networks.

Phase 1 · issuer only

Checkpoint and binding

Connector, engine and app step-up, plus the binding in the issuer's authorization host. Uses the card credential the agent already has. No network changes.

Phase 2 · with the networks

Scoped agentic tokens

Mint per-purchase tokens through Visa Intelligent Commerce and Mastercard Agent Pay. Limits now live in the network too, so stand-in processing respects them.

Phase 3 · with merchants

Signed carts

Bind a signed cart to the token request so the cart that was approved is the cart that is charged. Closes the last row of the failure table.
