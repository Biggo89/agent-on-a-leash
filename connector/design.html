Leash Wallet — Connector Design

How a cardholder plugs the Wallet Control Layer into an AI agent the way they plug in Gmail or GitHub. One URL, a login to their payment app, a consent screen, done. The agent gets a handful of tools. The cardholder keeps every decision that matters in the app.

Status built and verified Date 24 Sept 2026 Owner Nakya Source connector/README.md

The short answer

Build the connector as a remote MCP server with OAuth 2.1. That is exactly what the Gmail and GitHub connectors are under the hood. Our existing FastAPI service is the resource server. The mock Payment App plays the authorization server. The cardholder pastes one URL, logs into the app, sees a consent screen in the app's own look, and the agent has its tools. No API keys, no config files.

The connector is thin. It re-implements nothing in the engine. It owns three things: the token check, the mapping from token to cardholder and card, and a curated set of tools.

What exists now. Everything on this page is implemented in the wallet-control-layer project and verified end to end against the official MCP Python client and the phone in a browser. Two details changed from the first draft, each explained where it occurs: tokens are verified by introspection rather than a signed JWT, and the mock app lives inside the project beside the sandbox replica.

What the customer experiences

Six moments, in the order they happen. The consent screen in step 3 is where the experience is won or lost.

  1. Add the connector

    In Claude: Settings, Connectors, Add custom connector, paste the URL. Claude fetches the server's metadata, registers itself as a client, and opens the login page. ChatGPT and Claude Code do the same from the same URL.

  2. Log in to the Payment App

    The mock app's own login screen, not a generic OAuth page. Fake credentials, real look.

  3. Consent, phrased as a mandate

    No scopes like payment:write. Three short lines: which agent is asking, by the name it registered with. Which card it gets. What it can never do.

  4. Set up the leash in the chat

    The cardholder types the instruction to the agent in their own words. The agent calls propose_mandate. The draft appears on the phone with every span that became a rule highlighted. The cardholder confirms on the phone, not in the chat.

  5. Shop

    The agent calls request_payment. Approve and decline come back in a millisecond with the plain-language explanation. A step-up pushes to the phone with the countdown, and the agent is told the cardholder has been asked.

  6. Stay in control

    The app has a Connected agents page, like Google's third-party access page. Revoke there and two things happen at once: the token dies and the mandate is revoked. The agent's next call gets a clean "access revoked" answer, not a crash.

The decisions that make it elegant

  • Consent and confirmation never pass through the agent.

    The agent's token can only carry scopes for proposing, requesting and reading. The scopes that confirm a mandate, resolve a step-up or amend a limit exist only for the app's own session. This is the connector-level version of "no LLM in the decision path", and it belongs on the consent screen as a sentence.

  • Curated tools, not the OpenAPI dump.

    The Python MCP SDK can generate one tool per FastAPI route. Don't. The agent sees five verbs. Their descriptions carry the rules of the leash, which is the cheapest way to make a foreign agent behave: fewer declines, better demo.

  • The token binds cardholder, card and agent.

    A signed JWT with the cardholder as subject, the card, the agent's client id and the scope. The connector maps it to the Supervisor. The Supervisor is single-tenant today. For the mock, one session per subject and nothing else changes.

  • Step-up stays out of band.

    MCP has elicitation, where the server asks the client to ask the user. Tempting for step-ups and wrong for them, because the agent mediates the question. Use it at most for a compiler open question. Payment consent goes to the phone.

  • Return fast, let the agent poll.

    A step-up must not block the tool call for two minutes. Return pending with the authorization id and a human-readable line. payment_status resolves it.

  • Errors in cardholder language.

    The service already returns explanations. Pass them through as the tool result text: "CHF 391.50 exceeds the CHF 250.00 limit you set in the app", never "HTTP 409".

Plumbing

Discovery chain

The MCP authorization spec fixes this sequence, which is why any client finds its way with no configuration.

  1. The client calls /mcp without a token and gets a 401 whose WWW-Authenticate header points at /.well-known/oauth-protected-resource.
  2. That document names the mock app under authorization_servers.
  3. The client reads the app's /.well-known/oauth-authorization-server.
  4. It registers itself at the registration_endpoint and receives a client id. Claude also accepts a manually entered id and secret, but dynamic registration is what makes it one paste.
  5. PKCE authorization-code flow: /authorize shows login and consent, /token issues an opaque token bound to the connector as its resource.
  6. Every MCP call carries the bearer token. The connector asks the app whether it is live (RFC 7662 introspection, cached for a few seconds) and checks the scope against the tool.

Introspection rather than a signed JWT with a JWKS, as the first draft said. It needs no key material and no dependency, and it makes Revoke on the phone immediate: the token dies at its source and the agent's next call is a 401. An issuer with a real key infrastructure swaps the verifier, which is one method.

Who signs in

The personas on the sign-in screen come from the organizers' data pack. The customers file gives the person, the accounts and cards files give their everyday card and its account limit, and the authorization history gives the device the card is normally used from, which becomes the token's device id, and the purchase count that orders the list. The last four digits are derived from the card id and the PIN is not checked, and the screen says so. The engine judges a persona's agent against the same history the fixtures use.

Demo

claude.ai runs in the cloud, so it needs a public HTTPS URL for the MCP endpoint and for the authorization server. The one-process launcher mounts the app under /app of the service, so one tunnel covers both.

cloudflared tunnel --url http://localhost:8010

Claude Code needs no tunnel. The connector is documented as an extra after the beats in DEMO.md. If the venue Wi-Fi dies, the offline demo is untouched.

Where it lives

The MCP server is the connector package beside service in the leash source tree: auth, orders, the errand, rendering, the transport by hand, and the routes. Mounted on the same app.

The mock Payment App is payment_app inside the project, beside the sandbox replica, so it shares the one environment and the one check. Not folded into the leash demo or the playground, which each already have one job.

Its screens are the leash demo's screens. The app serves the demo's source tree and loads the same two stylesheets, whose tokens were sampled from one-digitalservice.ch, and the home screen runs the demo's own phone component and settings editor, fed by the connector's errand. One design system and one phone, with no copy to keep in step.

Positioning

Google's Agent Payments Protocol and Visa's Trusted Agent Protocol both use intent mandate and cart mandate for the objects this project already has. Borrowing that vocabulary in the tool names costs nothing and makes the connector read as a standard rather than a hackathon adapter.
